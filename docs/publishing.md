# От карточки до публикации

## Формирование записей

Для новой карточки или существенного обновления PostgreSQL записывает подготовленную версию отдельно для сайта и конкретного Telegram-чата, если они выбраны у канала. Запись содержит снимок заголовка, краткого текста, ссылки на источник, номер версии, приоритет, срочность и срок годности. `expires_at` рассчитывается от времени исходной публикации плюс максимальный возраст материала.

Если для того же события и адресата уже ждёт более ранняя версия в `pending` или `review`, она получает статус `expired` с причиной замены. Новая версия наследует наивысший приоритет и признак срочности из ещё свежих заменённых записей. Опубликованные версии остаются в истории. [Запись в очередь](../backend/internal/postgres/publications.go)

## Согласование

При включённом согласовании новые записи создаются в `review`. Одобрение переводит версию в `pending`, отклонение — в `rejected`. Решение хранится вместе с записью и относится к одной площадке. Повтор такого же решения идемпотентен. Включение согласования возвращает ранее автоматически поставленные в очередь записи на проверку, если для них нет явного одобрения. Отключение согласования применяется к новым версиям. Ожидающая запись в `review` требует решения для перехода в очередь.

## Выбор времени выпуска

Worker проверяет сайт и Telegram отдельно. Перед захватом проверяет активность канала, актуальность площадки и получателя, состояние согласования и срок годности. База выбирает срочные прежде резервных, затем по убыванию приоритета и по ID. Запись атомарно переводится из `pending` в `sending`.

- **Срочные** отправляются в ближайшем подходящем цикле. Тихие часы блокируют выпуск, пока в канале не включено `urgent_outside_hours`. Минимальная пауза между публикациями к срочным не применяется.
- **Резервные** отправляются вне тихих часов. Запись должна провести в очереди минимум `reserve_after_minutes`. Если для площадки уже есть отправленная публикация, от последней отправки должно пройти не меньше максимума из `reserve_after_minutes` и `min_interval_minutes`. При пустой очереди worker завершает проверку без отправки.
- **Тихие часы** задаются целыми часами в часовом поясе канала, включая окна через полночь. Начало входит в окно, конец открывает выпуск.

## Куда уходит результат

**Сайт.** Адаптер возвращает ID записи очереди. После фиксации `sent` Go API отдаёт снимок через `GET /api/v1/site/news`. Панель читает этот API. В ответе время `published_at` соответствует времени выпуска на сайте. Несколько опубликованных версий события могут быть видны в ленте. [Адаптер сайта](../backend/internal/publishing/website/website.go)

**Telegram.** При наличии токена worker отправляет жирный заголовок, курсивный краткий текст, источник и подпись канала с ссылкой через пустую строку. Для текста используется Bot API `sendMessage`, для фото/видео — `sendPhoto`/`sendVideo`, для альбома — `sendMediaGroup`. Вложения сначала загружаются в приватный S3 и затем читаются оттуда для отправки. [Медиа и ограничения](media.md). Для новой версии ищет последнюю ранее отправленную версию того же события для того же чата. Её ID передаётся как параметр ответа, а пост получает префикс «Дополнение». После успеха ID нового сообщения сохраняется в `external_id`. Если токен не настроен, worker пропускает Telegram-очередь до изменения конфигурации или истечения сроков. [Адаптер Telegram](../backend/internal/publishing/telegram/telegram.go)

## Состояния очереди

| Статус | Что означает |
| --- | --- |
| `review` | Версия ждёт решения оператора |
| `pending` | Версия готова к выпуску и ждёт условий по времени или приоритету |
| `sending` | Worker захватил запись и выполняет доставку |
| `sent` | Площадка успешно приняла версию, либо сайт опубликовал её в БД |
| `rejected` | Оператор отклонил версию |
| `expired` | Версия устарела, заменена новой, или её адресат больше не выбран |
| `failed` | Доставка завершилась определённой ошибкой |
| `uncertain` | Telegram мог принять версию, но результат неизвестен |

После прерывания доставки цикл возвращает запись сайта из `sending` в `pending`, а запись Telegram переводит в `uncertain`. Пока у события есть неопределённая отправка в этот чат, worker не захватывает следующие версии этого же события для этого адресата. Это предотвращает отправку потенциального дубля и потерю цепочки ответов. Автоматического повтора для `failed` и разрешения `uncertain` через панель пока нет.
