# Правила работы с репозиторием

При каждом изменении логики или кода в том же наборе правок обновляй соответствующий файл в `docs/`. Сверяй документацию с итоговой реализацией перед завершением задачи.

- Опиши, что изменилось во входных данных, обработке, выходе и переходе данных между компонентами. Если затронуты хранилище, состояния, ошибки, конфигурация или порядок запуска, обнови соответствующие разделы.
- При изменении API синхронизируй `api/openapi.yaml` и документ управления. При изменении схемы PostgreSQL обнови описание таблиц, связей и миграций. При добавлении компонента обнови карту репозитория и схему потоков.
- Проверь команды и относительные ссылки, которых коснулись правки. Фиксируй текущее поведение по коду, а запланированные функции обозначай явно.

Оглавление и ссылки на тематические документы находятся в [docs/README.md](docs/README.md).

## Ветки, этапы и PR

- Разработку веди во временной ветке от `main`. Продолжай текущий этап в его ветке, пока пользователь явно не объявит этап завершённым или не подтвердит завершение в ответ на твой вопрос.
- Выполнение отдельной задачи не означает завершение этапа. Создание коммита или PR также не завершает этап автоматически.
- PR в `main` вливает пользователь. Для слияния силами агента требуется отдельное явное поручение пользователя на конкретное слияние.
- Пока такого поручения нет, оставляй PR открытым и продолжай работу в ветке этапа. Не переноси изменения в `main` напрямую.
- Пиши заголовки PR и коммитов только на английском. Для коммитов используй шаблон `<area> stage N: <summary>`, где `area` — область разработки, например `backend`, `frontend` или `api`. Пример — `backend stage 2: match Russian word forms`.
- В заголовках и описаниях PR и коммитов указывай только изменения, которые фактически внесены в код и входят в соответствующий diff. Планы, ход работы, результаты проверок и развёртывание сообщай отдельно.
